# Q/K 局部修订后发现的 MLP 运行域冲突

本次用户授权只覆盖已审查的 Q/K 局部域。该修订已实现；下面的 MLP 问题没有包含在授权中，当前没有继续扩域。

同一公开问题“隐私计算如何保护问题？”在数值版本 `v1-f12-qk-local-20261013` 下完整执行160物理槽、28层R1 Embedding，耗时78.0945秒。首个域失败不再位于首层K RMS，而是第2层（零基编号）MLP的 `floor12(SiLU(gate) × up)`，即down_proj输入。此前算子未记录域失败。

矩阵形状为160×3072，共6个元素超过仍生效的abs≤256（f12整数1048576）界。最大绝对值位于物理位置0、特征55，该位置有效：

| 同一输入、同一算子、同一位置 | 值 |
| --- | ---: |
| R1 实际 f12 整数 | 12993396 |
| R1 对应实数 | 3172.2158203125 |
| R0 float32 对应值 | 3175.049560546875 |
| R1 超出256的幅度 | 2916.2158203125 |
| R0 超出256的幅度 | 2919.049560546875 |

有效位置范围分别为R1 [-2479.41943359375,3172.2158203125]、R0 [-2482.677001953125,3175.049560546875]。全矩阵R0/R1最大绝对差为3.257568359375。R0通过原Transformers的down_proj前向输入钩子捕获实际SwiGLU乘积，并完整跑完同一28层Embedding；未用手写替代浮点MLP。由此可确认实际模型在该公开输入上就会产生远大于256的该中间值，不是仅由R1实现异常引起。

NUM-003的主干运行域和NUM-004据此建立的算子中间界仍适用。R1按原失败规则保留失败标志并完成后续固定计算，最后输出e=0及零向量；这不是成功Embedding，不可作为资料准备成功结果发布。不能仅把这个张量阈值改为4096就直接继续宣称正确：它同时是down_proj的输入，必须单独复核完整点积、权重实际范围/行范数、截断顺序及2^56工程预算，且后续仍可能出现其他域失败。

建议下一步先审查SwiGLU乘积与down_proj这一局部连接的可行域方案，形成具体可审查的新边界，再决定是否修改设计。当前只提交上述事实证据，保持MLP及其他主干256不变。原始K域失败记录未覆盖；新JSON、R1/R0公开诊断数组以 `models_qk_revision_*` 独立保存。
