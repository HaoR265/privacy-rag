# 冻结 v1.0.3 后的等价优化方向与规范边界（只读分析）

2026-10-13。本次没有修改 native、冻结 manifest 或生产启用门，没有执行候选 GC/优化协议。下面的字节数来自实际实现帧、公开固定形状及整数推导，不能解释成运行时间或安全认证。同名 JSON 保存源文件/规范哈希与精确数值。

## 当前瓶颈分解

成套 M2048 修订增加了秘密 guard、改变数值 cap，但没有改变 BFV 调用处、gamma 逐坐标调用、32 输出行投影 tile、固定模型尺寸或生成槽数。因此原 BFV 通信子集的调用计数仍适用：非空 query 有 1,162,678,272 次单目标受控返回、308,304,077 个输入密文帧，计入的应用层消息至少 18,499,630,136,753,376 bytes（十进制约 18.50 PB）。新增 guard 和其他 OT/布尔运算仍不包含在这个 BFV 子集内。

| 返回类别 | 固定返回次数 | 占返回总数 |
|---|---:|---:|
| 普通和 down 投影 | 788480000 | 67.82% |
| 私有 gamma | 282421248 | 24.29% |
| Token embedding 的 19 块 | 52881408 | 4.55% |
| 256 次生成输出头 | 38895616 | 3.35% |

每次返回目前有 457,505 个 AND 半门，原始表项为 14,640,160 bytes，补齐成 224 个 64 KiB 块。GC 表帧占上述已计入子集约 92.40%。只合并消息、增加 GPU 或预生成 Enc(0) 不会消除这些表项。

## 最小且可明确证明的等价改变：固定 60 轮除法

`native/src/bfv.cpp:203` 起的 Decoder 先归约得到 `0<=v<q`，构造 420 位分子 `N=v*2^59+floor(q/2)`，然后做 420 轮 361 位恢复除法。其实

`0<=N<(2^59+1/2)*q<2^60*q`。

所以 `floor(N/2^60)<q`，当前循环处理完前 360 个高位时尚不可能减去 q。可将这些高位直接接入秘密 remainder，即 `remainder=N>>60`（360 个分子高位加一个公开零高位），然后固定处理低 60 位。每轮仍先左移接入下一位、精确试减公开 q、秘密选择；最后只解释商的低 59 位。

**必须保留 60 轮，不能缩成 59 轮。** 当 `v=q-1` 时，完整整数商可以等于 `2^59`，最后模 t 才成为零。错误地忽略这一位会改变低位解码结果。相位、分子和余数仍保持既有 361/420/361 位；没有浮点近似、局部份额截断或私钥输入 GC。

保持其他门实现不变时，门数从 `5*361+2*420+3*361*420=457505` 变成 `5*361+2*420+3*361*60=67625`，表帧变为 34 个 64 KiB 块。按完全相同的模型调用次数，已计入 BFV 子集变为 4,000,939,070,651,616 bytes，约 4.00 PB。这个结果说明减少大量公开必为零的商前缀有意义，也说明它仍远不足以支撑本机整模型 R2。

数学恒等式另以实际 q 的 1,058 个公开值（含取整边界和 q−1）及小奇数 q 的 14,994 个穷举值核对一致。这只是整数参考调试，**没有运行新 GC 或新 R2 实现**。若后续实施，必须更新精确门数、GcBatchChannel 的固定 public expected gates、生产/开发源码版本、工件及独立真实两方执行证据；继续保留 fresh mask、fresh Enc(0)、独立 GC 输入 OT 和只给 C 的目标份额输出。

此改变符合 `参数与接口.yaml` 的 `BFV.controlled_decode.GC_computation`（1350–1353 行）、`width_rules.division`（1363–1367 行）及 `actual_integer_circuit_layout`（1368–1371 行）。这些字段锁定精确函数和位宽，没有要求执行明知商为零的 360 个无用轮次。

在这一步之后，可再对公开常量 q / floor(q/2) 专门实现加减器：公开常量位只需一个 carry AND，无须每位两个通用加法 AND；条件选择保持一个 AND。按保守固定一门每位构造，门数可进一步为 `4*361+420+2*361*60=45184`，同子集约 3.162 PB。不能通过检查秘密 wire label 来决定省门；只允许依公开 q 的位分支。这是第二个未实施候选。

## 可在现有输出契约内做的批量化

### 跨公开行 tile 复用同一输入密文

当前 `Transformer::project`（model.hpp 的 project 函数）每 32 行调用一次 private_linear，因而同一 x 在每个 tile 重复加密。v1.0.2 已经实际证明并实现了同一次 private_linear 内的输入密文复用。把这一已实现机制延伸至一个完整公开投影，可以用绑定当前 SecureOps/session/configuration/input-shape 的短生命周期 handle，逐 tile 流式读取 S 的权重；不要一次构造完整 LM head 稠密权重副本。

每个输出仍是独立结果密文、全系数新掩码、新鲜 Enc(0)、一个目标系数 GC。它不把多个输出塞入同一个返回密文，也不复用零密文或掩码。可以缓存同一输入密文的 NTT 表示，省去每行重复的本地正向 NTT；这不减少输出帧，实际 CPU 收益需另行测量。异常退出时 handle 禁止恢复/跨会话复用，预留随机材料按已有规则 burn。

### gamma 的对角批量调用

目前 RMS 每个 h_i 单独调用 `private_linear({h_i},{{gamma_i}})`。可以先按相同数值顺序得到整行 h，再把 gamma 表达为 S 持有的公开形状对角矩阵，对同一个 h 输入密文逐行执行单目标返回。第 i 行只有公开位置 i 放私有 gamma_i，其他位置为公开零；无需分配 H×H 稠密数组，逐行/逐 tile 生成即可。权重为零仍走完整固定 NTT、掩码和重随机化路径。

这是 `operations.private_gamma`（参数与接口.yaml 829–838 行）的同一个私有 f12×f12 线性算子：raw f24、floor12、原定输出检查不变，gamma 不公开。它减少输入加密数量，**不会减少 282,421,248 个 gamma 结果系数的受控解码数量**。把 gamma 改用 OT 乘法，则会触及 `cryptographic_backends` 的私有权重→BFV 分工，不属于这里的等价调用批次优化。

若同时完成整投影输入复用和 gamma 对角批量，输入密文计数的静态候选为每 token `19+729+196=944`，加每次 LM head 一个输入。完整 query 共 1,358,672 个输入密文，较当前减少 482,812,844,248,800 bytes（约 0.483 PB）；输出数量完全不变。不能把这个节省误乘到全部返回或宣称它解决了 PB 级瓶颈。

### Token one-hot 构造与 GC/OT 公共批次

当前 token() 对 19×8192 个候选逐次 equal，重复分解同一秘密 ID。可在保留原 invalid-ID→failure→dummy-ID0 语义后，一次 A2B，使用公开固定的秘密 one-hot 树并批量 B2A，输出全部 f0 指示位。树的截枝只能依公开词表/填充边界，不能依秘密 token。然后仍执行全部 19 个 BFV 块，按原顺序得到 f12 分块结果并求和。

这与 `operations.token_embedding_lookup` 的 one-hot→LinearPrivateWeight→固定分块和（782–798 行）一致，可以复用 v1.0.3 公共 LUT 中已验证的树思路，但不能把私有 Token 表直接换成 public lookup。它减少未计入 18.50 PB 子集的布尔/OT 成本，BFV 返回次数仍为 52,881,408。

独立输出的 GC 输入 OT、标签帧和半门表可按公开 output batch 合并传输；每个 wire 和材料仍独立、每个目标仍独立解码。单纯批帧不会减少逐目标逻辑 AND 数量，故不是主要 GC 表负载的替代解法。

## 必须先明确修订协议布局的方向

| 方向 | 当前锁定字段/规则 | 需要补齐的内容 |
|---|---|---|
| 一个返回密文承载多个结果系数 | packing 的 X/W 公式、target_coefficient=d−1、`forbidden.assumed_multi_output_reuse_optimization`（1312–1327 行）；协议文档 84–90 行逐行重复单点积 | 新权重多项式、公开目标索引集合、跨输出污染与负循环回绕证明、掩码和新 Enc(0) 的结果对象定义、每个目标解码及噪声界/帧/材料工件。不能把已允许的输入复用等同于已经允许结果多目标布局。 |
| 把 Token 的 19 个块先同态相加，只解码最终和 | token 的固定分块结果求和（784–798 行）；packing.long_input（1319 行）；协议文档 90 行每块产生原始结果份额后再累加 | 改写“块结果何时返回”的调度契约，证明多密文乘法结果相加后的准确噪声界；不能直接套用当前每返回一次乘法的 ART-002 依据。 |
| BatchEncoder、旋转、密文乘密文 | packing.forbidden（1323–1328 行），CRY-004 | 当前明确禁止；不能作为普通工程批处理偷偷加入。 |
| 更低数据层/更小 q、减少环位宽或安全参数 | 实际数据层六素数/q/parms_id（1293–1305 行）、已绑定 ART-002 上下文守卫 | 新参数/层级和误差证明并重新登记；本分析不视为冻结配置下的等价电路优化。 |
| 重用 Enc(0)、只掩码输出位置、发完整密文 | linear_return（1336–1338 行）、controlled_decode（1341–1361 行）、CRY-005 | 直接违反现有保护边界，不是可接受的成本优化。 |

多结果系数打包确有值得研究的代数形式，但不能先报未经验证的输出复用倍率。例如同一长度 d 输入对多个权重行可考虑把各权重反序多项式移入互不重叠的卷积区间；若完全不依赖回绕，区间宽度为 `2d−1`，公开容量只能按 `floor(16384/(2d−1))` 推导。对 d=1024/2048/3072/6144/8192 分别为 8/4/2/1/1；Token 的满 8192 块不能因此获得多行打包。独立 gamma 坐标的输入 h_i 不同，也不能把 d=1 的容量数字直接当作 H 个独立乘法都能无污染输出。以上只是新布局研究的约束，不是已成立协议。

## 应怎样使用这份分析

最小工程顺序是先精确 60 轮除法，再公开常量加减器，再处理有明确收益上限的输入复用/one-hot 批次；每步都必须单独形成等价与真实两方证据，不因数学推导而重写冻结 v1.0.3 的运行历史。更大幅度减少返回次数，需要先明确上述协议输出布局条款。

即使假设 GC 表完全免费，保持当前“一标量输出一完整 c1”的组织方式，仅 c1 帧仍有 914,479,015,919,616 bytes，约 0.914 PB；这只是当前布局的静态底线，不是所有允许隐私协议的信息论下界。继续叠加线程、GPU、预计算或编码压缩无法据此声称整模型可运行。所有候选保持为只读设计分析，生产 gate 不因此开启。
