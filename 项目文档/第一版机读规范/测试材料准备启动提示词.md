# 测试材料准备启动提示词

使用方式：提供整个「第一版机读规范」文件夹，再向执行AI发送下方提示词。这是独立的材料准备任务；仅阅读本文件不触发执行，也不把材料类别或数量变成项目正式测试与验收要求。

```text
请为本项目第一版隐私RAG系统搜索、整理并生成一套可供后续调试、演示和测试使用的材料，重点是D提供的文档与Q问题集合。

D表示资料提供方，Q表示查询问题集合；项目中的提问方角色仍称为U，每道问题须绑定一个user_id。请交付实际材料，不只给选题建议、搜索链接或空目录。

一、任务范围

先阅读随附「第一版机读规范」中的项目背景、资料与授权流程、输入格式和容量限制，以当前版本为准，不依赖其他项目讲解文档或历史对话。

本次开展资料搜索、文本整理、问题生成、证据核对和材料组织。测试方法、评分公式、性能门槛与最终验收标准仍留待后续讨论；材料准备不等于运行系统测试，也不据此宣称协议已经安全或系统已经通过验收。

二、场景与来源

自主选择一个资料充足、事实容易核对、确有跨机构协作需求的主要场景。可优先考虑设备运维、技术支持或联合研发资料协作。简要说明选择理由后继续，不必等待我确认常规选材决定。

先检查工作区现有材料，再搜索外部公开来源。优先使用官方手册、机构技术资料、公开项目文档及授权明确的数据集；实际阅读内容后选用，不能只凭搜索摘要生成文档和答案。

区分真实发布者与演示中的模拟资料提供方。把公开资料分配给D1、D2等模拟机构时，标明模拟归属，不冒称真实机构参与项目或授权。

记录来源标题、发布者、URL、版本或日期、获取日期、使用许可和获取情况。遵守来源使用限制；许可不明时如实记录，不宣称可自由再分发全文。

分开标记真实公开资料、基于来源改写的资料和完全合成资料。真实事实保留出处，改写保留来源映射，虚构机构、项目代号、数值和业务记录明确标记synthetic，不伪造来源。

三、D端文档

围绕同一业务主题组织相互关联的资料，形成可阅读的文档正文，不把全部资料写成针对问题定制的问答卡片。保留适用对象、版本、时间、条件和必要上下文，清理导航及重复内容时不能丢掉决定答案的限定条件。

每份文档设置稳定doc_id、provider_id、版本、路径、来源记录和allowed_user_ids。设置不同模拟用户的授权差异；授权表示资料可以参与该用户的问答，不表示用户可以直接读取原文。

整理为系统接受的UTF-8 TXT或Markdown正文。网页、PDF可以作为外部来源，但先转换为已核对文本，不给第一版系统新增复杂PDF/OCR处理要求。

保留原始文档、清洗后正文与切块的映射。按现行tokenizer和切块规则形成块记录；原始文档可以较长，256 Token限制针对块正文。不得为凑数量重复资料或跨不同授权合并文本。

四、Q问题集合

根据已经整理并核对的资料生成自然、独立、单轮的问题。每题绑定question_id、user_id和资料/授权快照。问题应像实际使用者提出的请求，不直接复制证据，不泄漏参考答案或评估用命中文档编号。

首批材料可包含以下类别，数量与分布由你根据材料质量自主安排，不作为验收门槛：

- 单份资料可支持的问题。
- 需要结合不同资料提供方信息的问题。
- 自然改写、相似实体或相近条件容易混淆的问题。
- 授权资料不足的问题，区分答案只在未授权资料中与整个资料集都没有答案。
- 同一问题在不同用户授权下，可支持的回答内容不同的配对材料。
- 涉及版本、时间或适用对象的问题；区分真正冲突与可由适用条件解释的差异。
- 要求整段资料导出的请求；其参考处理遵守现有产品边界，不把语言拒答视为密码安全证明。

按当前Top-2容量安排主体材料：多数可回答问题的必要依据应能落在一至两个实际切块中。确需更多块的问题单独标记限制，不预设当前系统一定答得出，也不修改资料事实来迁就容量。

可补充少量明确标注的合成项目记录或对照变体，使答案依赖所提供资料中的专属事实，而不是模型可能记住的常识。公开资料能被答对并不能证明系统确实检索了资料。

五、独立参考标注

为每题另存参考回答要点、逐条支持证据的doc_id/chunk_id及具体位置、授权依据、必要条件和无法从现有资料推出的内容。允许多组充分证据，不强行规定只有一个正确检索集合。

参考答案只能从该用户在指定快照下获准使用的资料推导，并采用概括表达。不能拿未授权资料、外部常识或模型编造内容补齐答案。资料不足时写明缺口，存在冲突时写明分歧及适用条件，不强造唯一答案。

原文证据可以保留在离线标注中，面向用户的参考回答不附原文片段。自动生成的参考答案须逐条回到资料核对，无法核实的标为待复核，不冒称人工审定。

标注表示资料支持关系与期望处理，不代表实际检索或生成结果。未运行系统时，不填造命中、得分、耗时或成功状态。

六、输入适配与隔离

读取现行规范的真实tokenizer和长度规则，分别核对问题正文、带指令的Embedding输入、文档切块等预算，不用汉字数代替Token数。优先复用现成工具；无法实际分词时标记未核对。超长问题可另写保留原意的短版本，不能静默截断后仍沿用失效标注。

检查ID唯一性、文件可读性、授权引用、证据定位、版本一致性和重复情况。这些是材料自身的整理核对，不制定系统验收标准。

可信离线目录可以集中管理资料、问题和标注，实际使用时按角色分开导入：D端导入资料与授权，U端导入该用户的问题。参考答案、支持证据编号、问题类别等评估信息不能混入模型提示词，也不能作为普通查询输入发给S。不要新增服务方可读全部原文的导入旁路。

七、交付与执行

在独立「测试材料」目录保存实际文件，建议包括：

- README：场景、材料构成、来源与合成内容的区别、使用方式和已知限制。
- D_documents：可导入文档正文，以及来源、清洗与切块映射。
- documents.jsonl：文档ID、提供方、版本、路径、来源和授权信息。
- Q_questions.jsonl：问题ID、用户ID、问题文本和快照标识。
- snapshots.json：模拟用户、资料版本与授权关系的具体快照。
- reference_annotations.jsonl：离线参考要点、支持证据、处理类型与复核状态。
- sources.jsonl及材料清单：来源记录、数量、分类概况、版本与完整性信息。

已有工程存在合适格式时优先兼容，并说明字段映射。首批规模自行确定，先完成一套内容可靠、关系完整、可以使用的材料，再按缺口扩展。不要只建空文件夹或留下模板占位。

现在开始检查现有材料和规范，简要说明选定场景与搜集安排，然后直接进行搜索、整理、生成和核对。选材、编号、文件格式与常规整理方式由你自主决定；只有缺少必须由我提供的真实私有资料，或需要改变既定系统能力时才提出具体问题。
```
